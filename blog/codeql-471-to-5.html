CodeQL 报了 471 个漏洞，真正的只有 5 个

2026-11-20 · 作者 PHclaw

安全 #CodeQL #静态分析 #告警治理 #工程实践
Security 面板一片红：471 个未处理告警，其中 2 个 critical。 花了半天逐条看下来，真正值得改的是 5 处。 问题不在代码有多烂，在查询包选错了、第三方代码没排除、告警没有分级处理。

结论先说

代码扫描工具报的数字，和项目真实的安全状况，往往是两回事。这次的经历可以浓缩成三条：

  1. security-and-quality 会把代码质量问题也算成"安全告警"——471 条里有 309 条根本没有安全等级
  2. vendored 的第三方代码必须排除——246 条来自 skills/ 下的社区技能，那些代码不归本项目维护
  3. 批量 dismiss 要写理由——不是为了把数字清零，而是让留下来的每一条都有意义

最终数字变化：

471  →  98  →  94  →  0
     改查询包   真修5处   标记94条

现象：面板上有 471 个红点

给项目接入 CodeQL 时，我在工作流里写了：

- name: Initialize CodeQL
  uses: github/codeql-action/init@v3
  with:
    languages: ${{ matrix.language }}
    queries: security-and-quality

security-and-quality 听起来很全面——既查安全又查质量，有什么不好？

扫描跑完，Security 面板显示 471 个 open alerts。按等级拆开：

等级数量说明
quality（无安全等级）309纯代码质量，不是漏洞
high79需人工确认的模式告警
medium81同上
critical2需要看

按目录拆开，问题更明显：

来源数量
skills/（第三方技能）246
backend/192
frontend/26
其它7

一半以上的告警来自 vendored 的第三方技能——那些是社区贡献的脚本，各自有独立的许可证和维护者，本项目的改动不会回头修它们。

第一步：先看 Top 规则，别急着改代码

遇到几百条告警时，本能反应是"逐条修"。但先看规则分布，能省掉大量无用功：

80  py/empty-except              # except: pass，风格问题
60  py/path-injection            # 路径拼接，多数在技能脚本里读自己的资源
51  py/unused-global-variable    # 未使用变量
40  py/unused-import             # 未使用 import
38  py/unused-local-variable     # 同上
37  py/stack-trace-exposure      # 错误响应里带堆栈

前四条加起来 209 条，基本是"代码风格 + 静态分析噪音"。它们让真正重要的 critical 被埋在红点里——这才是最大的问题。

第二步：改查询包 + 排除第三方目录

一次配置改动，471 → 98：

- name: Initialize CodeQL
  uses: github/codeql-action/init@v3
  with:
    languages: ${{ matrix.language }}
    # 只跑安全类规则，去掉质量噪音
    queries: security-extended
    config: |
      paths-ignore:
        - skills/**              # vendored 第三方代码
        - '**/node_modules/**'
        - '**/dist/**'
        - '**/__pycache__/**'

两个变化：

  1. security-extended：只跑安全规则集，不把"未使用变量""空 except"算进来
  2. paths-ignore：第三方技能不归本项目维护，它们的告警既不 actionable，也会淹没自己代码的问题

这一步没有改任何业务代码，告警降了 79%。

第三步：从 98 条里挑出真正要改的

剩下的 98 条按规则分布：

规则数量判断
py/path-injection48多数已有 resolve + 工作区边界校验，误报
py/log-injection29日志面向运维，写入方已认证，低风险
py/stack-trace-exposure10真问题
py/partial-ssrf2设计使然（自定义模型端点）
py/incomplete-url-substring-sanitization2仅学术站点识别，不参与鉴权
其它7含 weak-hashing 等

值得真改的是 py/stack-trace-exposure。逐条看过去，5 处确实在把异常原文回给客户端：

位置原来的问题
全局异常处理message = str(exc) if settings.DEBUG——生产环境一旦误开 DEBUG 就泄露堆栈
Stripe webhook解析失败直接回 str(e)，报错里可能带签名片段
知识库重排降级except 分支回 str(e)
/health/ready免认证公开端点，回 str(e) 会泄露连接串和主机名
SSE 对话流f"执行失败：{exc}" 会原样显示在对话气泡里

修复：统一异常遮蔽，只给 trace id

新增一个模块，把异常原文留在日志里，响应里只给固定文案 + 追踪 ID：

def log_and_mask(exc, *, where: str, fallback: str = "服务暂时不可用"):
    """异常原文只进日志，对外返回固定文案 + trace id。"""
    trace_id = uuid.uuid4().hex[:12]
    logger.error("[%s] trace=%s: %s", where, trace_id, exc, exc_info=True)
    return trace_id, fallback

然后在各处替换：

# 改前
return JSONResponse({"error": str(e)}, status_code=400)

# 改后
trace_id, message = log_and_mask(e, where="billing.webhook", fallback="Webhook 校验失败")
return JSONResponse({"error": message, "trace_id": trace_id}, status_code=400)

用户报障时报 trace id，我们凭日志定位；攻击者拿不到文件路径、依赖版本、SQL 片段。

顺手把两个用 md5 生成 key 的地方换成了 sha256（限流 key 和缓存 key）。严格说这不是安全存储、属于误报，但换哈希成本为零，省掉以后每次解释。

第四步：批量 dismiss，但每条都写理由

剩下的 94 条不是"忽略掉就行"，而是按规则分组、逐条写明理由：

规则数量标记理由要点
py/path-injection48won't fix路径先 resolve 再校验，必须落在工作区/生成目录内
py/log-injection29won't fix日志面向运维，写入方已认证
py/stack-trace-exposure7false positive文案来自 humanize 函数，不含堆栈
py/partial-ssrf2won't fix自定义模型端点是产品能力（要连内网 Ollama）
py/incomplete-url-substring-...2false positive仅学术站点识别，不参与鉴权
js/insecure-temporary-file2won't fix开发期录屏脚本，不随产品分发
py/sql-injection1false positive表名过正则 + 白名单，值全部参数化

GitHub 会记录每条的 dismissed_comment，随时可在 Security → Closed 里恢复。以后新代码引入同类问题，仍会照常报警——dismiss 只针对当前这条，不是给规则开永久豁免。

三条可复用的规则

1. 查询包按用途选，不是越全越好

  1. 想给代码做全面体检 → security-and-quality
  2. 想对外展示可信的安全状态 → security-extended

前者适合内审阶段，后者适合长期挂着。

2. vendored 代码一定要排除

第三方库、技能、生成代码不归你维护。让扫描器扫它们，只会制造噪音。CodeQL 的 paths-ignore 一行就能解决。

3. 告警要分级处理，不要只做两头

面对几百条告警，正确的动作顺序是：

改查询包 → 排除无关代码 → 挑真问题修 → 剩余的逐条标注理由

直接 dismiss 全部等于没做扫描；逐条硬修 471 条则是浪费时间。

一句话总结

安全面板的价值不在于告警数量少，而在于每一条都值得看。 471 个红点等于没有信号；0 个 open + 94 条带理由的 closed，才是一个能用的状态。
