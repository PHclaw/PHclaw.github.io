一次 Git 合并丢了 500 个文件：三方合并的「静默删除」陷阱

2026-11-20 · 作者 PHclaw · 分类 Git / 工程实践

合并显示「干净」，CI 却开始报模块找不到、技能广场空空如也。 根因不是冲突解决错了，而是根本没有冲突——这正是最危险的地方。

结论先说

Git 三方合并有一个容易被忽略的默认行为：

当「一方删除了文件、另一方没有修改它」时，Git 会直接采用删除结果，不报冲突。

这意味着一次看起来完全干净的合并，可能悄悄丢掉一整个目录。本文记录我在合并 AgentFlow 完整版分支时踩到这个坑的完整过程、排查命令和三条可复用的防护规则。

现象：合并很干净，功能却少了

背景是这样的：一个分支为了精简产品，删除了控制台、工作流、知识库等模块以及 skills/ 下的技能目录；另一条分支（完整版）保留了这些能力。需要把完整版合并回主干。

合并过程没有任何冲突提示：

git merge refactor/phase1
# Auto-merging ...
# No conflicts.

提交、推送，看起来一切正常。但 CI 立刻开始报错：

TS2307: Cannot find module './nodes'

同时后端测试失败：/api/v1/skills/plaza 返回空列表——技能广场里一个技能都没有了。

诡异之处在于：本地开发时这些功能都还在。 因为本地工作树来自完整版分支，而主干上的文件已经不见了。

排查：用 diff-filter 找出「被删除的文件」

普通的 git diff 看不出问题，因为合并已经完成，两个分支的内容在合并提交里「一致」了。要把合并的另一个父提交拉出来对比：

# 列出「完整版分支有、合并后的 master 没有」的文件
git diff --diff-filter=D --name-only refactor/phase1 origin/master

这一条命令直接列出了 500 多个消失的文件：

frontend/src/components/workflow/nodes/index.ts
scripts/init.ps1
scripts/init.sh
skills/excel/SKILL.md
skills/pdf/SKILL.md
skills/academic-search/SKILL.md
...

按目录统计后发现主要集中在三处：

目录性质后果
skills/（11 个技能目录）业务能力技能广场返回空
frontend/.../workflow/nodes/前端模块TS2307 构建失败
scripts/初始化脚本文档里的命令失效

根因：三方合并的「删除 vs 未修改」

用 Git 的三方合并模型解释就清楚了：

     base（共同祖先）
      /        \
  master      refactor/phase1
  （删除文件）   （未修改文件）
      \        /
       合并结果

Git 对这种情况的规则是：

  • 一方删除、另一方未改 → 采用删除，不产生冲突
  • 一方删除、另一方修改 → 冲突（modify/delete），需要人工决定
  • 双方都删除 → 一致删除

所以最危险的不是第一种吗？不——正因为不报冲突，人不会停下来检查。modify/delete 冲突反而会强制你做决定。

这类「静默删除」常发生在：

  • 精简分支删掉了一批文件，而完整分支自合并基线后没有再碰过它们
  • 迁移目录结构时用了 git rm
  • cherry-pick 或 revert 之后再做合并

修复：从另一父提交恢复

确定这些文件应该保留后，直接从完整版分支检出：

# 恢复整个技能目录
git checkout refactor/phase1 -- skills/

# 恢复单个文件和脚本
git checkout refactor/phase1 -- \
  frontend/src/components/workflow/nodes/index.ts \
  scripts/init.ps1 scripts/init.sh

git add -A
git commit -m "fix: 恢复合并时被静默删除的文件"

提交后 CI 恢复：前端 tsc 通过，技能广场重新返回 26 个技能。

三条可复用的防护规则

1. 合并后固定跑一次删除检查

把这条命令加入合并后的检查清单：

git diff --diff-filter=D --name-only <另一个父提交> HEAD

看到不该消失的文件，就说明合并把「静默删除」当成了一致结果。

2. 「精简」优先用配置开关，不要直接删文件

如果目的是下线功能，更安全的做法是：

  • 前端路由用 feature flag 控制显隐
  • 技能用状态字段（published / archived）控制上下架
  • 脚本保留，文档里标注 deprecated

文件还在，合并就不会丢；功能是否可用由运行时配置决定。

3. CI 要覆盖「功能是否存在」，不只是「能否构建」

这次前端构建和后端测试其实都给出了信号：

  • TS2307 说明模块缺失
  • 技能广场测试断言返回非空，失败

如果 CI 只跑 lint 而跳过这两类测试，这个错误可能要到用户反馈才会发现。

一句话总结

Git 合并里最危险的冲突，是那些不报的冲突。 只要合并涉及「删文件」，就一定要用 git diff --diff-filter=D 复核一遍。
