RAG 检索不出东西？先查这 5 个地方（附真实排错过程）

2026-11-20 · 作者 PHclaw · 分类 AI / RAG / 工程实践

AI #RAG #知识库 #embedding #排错
知识库建好了、文档上传成功、界面一片正常——就是一条都检索不出来。 这类问题几乎都不是"算法不行"，而是链路上某一环静默失败了。 本文按排查顺序讲清楚 RAG 的 5 个关键检查点，全部来自 AgentFlow 的真实踩坑。

结论先说

一个能跑的 RAG（检索增强生成）链路只有五步：

上传文档 → 分块 → 调 embedding 端点生成向量 → 存向量库 → 提问时检索并注入上下文

任何一步失败都可能表现为"检索不出内容"。排查时按链路顺序查，不要一上来调相似度阈值。五个检查点：

#检查点最常见的失败表现
1embedding 端点有没有配一切正常，检索永远为空
2文档有没有真的分块上传成功，但检索无命中
3向量维度和模型是否匹配报维度错误或结果乱
4相似度阈值是否设得过高有结果但都被过滤掉
5检索到的内容有没有真正注入 prompt模型说"我不知道"，但明明检索到了

1. embedding 端点：最容易静默失败的一环

这是我们踩得最深的坑。Docker 镜像里没有装本地 embedding 模型——sentence-transformers 加模型权重要 2GB 以上，不适合塞进默认镜像。

所以设计上要求用户配置外部端点：

EMBEDDING_BASE_URL=https://api.example.com/v1
EMBEDDING_MODEL=text-embedding-3-small

问题在于：如果留空，很多实现不会报错，而是走本地推理路径然后失败。表现是：

知识库能建 ✅
文档能上传 ✅
点"检索" → 空列表 ❌

没有任何错误提示，日志里也看不出所以然。排查方向：

# 服务启动时主动检查 embedding 配置，缺了就直接报出来
try:
    service._get_embeddings()
except EmbeddingNotConfiguredError:
    # 明确告诉运维：不是算法问题，是配置没填
    raise RuntimeError("EMBEDDING_BASE_URL 未配置，知识库无法工作")

规则一：embedding 端点缺失必须"响亮地失败"，不能静默。用户宁愿部署时就报错，也不要上线三天后才发现知识库一直是空的。

2. 分块：上传成功不等于真的入库

文档上传后要经过切分器（chunker）才能变成向量。常见坑：

  • PDF 是扫描件（图片），没有文字层 → 分块数为 0
  • 分块太大 → 一个块里塞了太多主题，检索精度差
  • 分块太小 → 语义被切断，命中了也看不懂

排查方法：直接看分块数，而不是看"上传成功"的提示：

chunks = splitter.split_documents(doc)
print(f"文档 {doc.name}: {len(chunks)} 个分块")
if len(chunks) == 0:
    # 扫描件 PDF 要有 OCR 流程，不能静默跳过
    raise ValueError("分块数为 0：检查文档是否含可提取文字")

规则二：上传成功后立刻校验分块数 > 0，否则后面全是无用功。

3. 维度与模型匹配

embedding 模型决定向量维度。比如：

模型维度
text-embedding-3-small1536
text-embedding-ada-0021536
bge-large-zh1024

换模型不重新入库是另一个高频坑：旧向量是 1536 维，新模型返回 1024 维，查询时相似度计算直接报错或者返回乱结果。

我们的做法是把 embedding 端点和对话模型分开配置：

# 对话模型——随便换，不影响已有向量
LLM_BASE_URL=...
LLM_MODEL=deepseek-chat

# 向量模型——换一次就要重新入库，单独配置
EMBEDDING_BASE_URL=...
EMBEDDING_MODEL=...

这样用户想换个便宜的对话模型试效果，不会连带把整个知识库搞坏。

规则三：换 embedding 模型 = 重建知识库。界面上要有明确提示，不能让用户在设置页随手一改。

4. 相似度阈值：别急着调

很多人检索不出内容的第一反应是"阈值太高了，调低点"。但按顺序排查时，这应该是第四步——前三步都确认正常后才看阈值。

阈值设得太高的表现很特定：

检索返回了候选片段 → 但都被阈值过滤 → 最终注入上下文的是空

排查方法：把过滤前的 top-k 结果打印出来，看相似度分布：

results = vectorstore.similarity_search_with_score(query, k=10)
for doc, score in results:
    print(f"{score:.3f}  {doc.page_content[:60]}")

如果最高分只有 0.4，阈值设 0.7，那问题在阈值；如果最高分是 0.0 或报错，问题在前面几步。

规则四：先看到原始分数，再决定阈值。

5. 注入：检索到了但没进 prompt

最后一步也很容易出错——检索成功，但拼接 prompt 时把结果丢了：

# 错误示例：context 变量没被用进 prompt
context = "\n".join(d.page_content for d in results)
prompt = f"用户问题：{query}\n请回答。"  # context 呢？

# 正确：明确把 context 放进 prompt
prompt = f"""参考以下内容回答问题。
如果材料中找不到答案，就说"资料中没有"，不要编造。

参考资料：
{context}

问题：{query}
"""

规则五：在 prompt 里明确要求"找不到就说没有"。否则模型会基于自己的知识编答案，你以为 RAG 生效了，其实模型在自由发挥——这比检索失败更危险，因为它看起来是"正常工作"的。

一张排查流程图

检索不出内容
   ↓
① 看 embedding 端点配了吗？ ── 没配 → 报错，别静默
   ↓ 配了
② 看分块数 > 0 吗？ ── 0 → 检查文档是否有文字层
   ↓ >0
③ 看向量维度对吗？ ── 不匹配 → 重新入库
   ↓ 对
④ 打印原始相似度分数 ── 都很低 → 调阈值/改分块
   ↓ 有高分
⑤ 看 prompt 里有 context 吗？ ── 没有 → 修拼接逻辑

一句话总结

RAG 检索不出内容，九成不是"算法不行"，是链路上某一环静默失败。 按 端点 → 分块 → 维度 → 阈值 → 注入 的顺序查，每一步都要"响亮地失败"。
